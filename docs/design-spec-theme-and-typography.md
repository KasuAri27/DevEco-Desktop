# DevEco Agent Desktop · 主题与字体重构规格书

> 本文档是设计规格，不是实现代码。目标读者：负责把本规格落地到 `styles.css` / `index.html` / `app.js` 的实现方。

## 0. 范围与不变量

**要改的：**
- `styles.css` 的设计令牌（`:root` 变量）、字号体系、硬编码颜色
- `index.html` 新增主题切换入口（设置面板内）
- `app.js` 新增主题状态读写逻辑

**不要改的：**
- 现有 DOM 结构的语义和 id（除非本文档明确要求新增）
- `desktop/*.cjs` 的 IPC 契约（除非第 5 节明确要求新增一个 IPC 通道）
- 所有涉及 Provider、账号、配置的业务逻辑

**硬性约束：**
- CSP 已锁死 `style-src 'self' 'unsafe-inline'`，`connect-src 'none'`——不能引入外部字体文件、外部 CDN、外部字体 API。字体只能用系统已装字体栈（见第 2 节）。
- 不引入任何新的 npm 依赖来做主题切换，纯 CSS 变量 + 一个 `data-theme` / `data-color-mode` 属性即可。

## 1. 主题总览：两套色相 × 两种明暗 = 4 个具体外观

用户能选的是**色相**（红 / 蓝）和**明暗**（浅色 / 深色），两个维度正交，一共 4 种外观：

| 色相 | 浅色模式名称 | 深色模式名称 |
|---|---|---|
| 红 | 战狼红（浅） | 战狼红（深） |
| 蓝 | 冷锋蓝（浅） | 冷锋蓝（深） |

**UI 文案只展示色相名**：「战狼红」「冷锋蓝」。深浅切换是独立的第二个开关（例如「跟随系统 / 浅色 / 深色」），不叫「战狼红·深色模式」这种复合名字——两个选择器分开摆放，设置面板里一个管色相，一个管明暗。

**命名由来说明（供实现方理解设计意图，不要出现在 UI 文案里）：** 「战狼红」对应华为品牌红 `#C7000B` 一脉的强调色；「冷锋蓝」对应 HarmonyOS 系统蓝 `#0A59F7` 一脉。两个名字只是色相的昵称，不代表功能差异——两套主题的组件结构、交互行为完全一致，只有颜色令牌不同。

**默认值**：色相默认「冷锋蓝」，明暗默认「跟随系统」（即读 `prefers-color-scheme`）。

## 2. 字体与字号

### 2.1 字体栈（新增 3 个变量，替换原来写死在 `:root` 的单一 `font-family`）

```
--font-ui:   "Segoe UI Variable Text", "Segoe UI", "Microsoft YaHei UI",
             "PingFang SC", "HarmonyOS Sans SC", system-ui, sans-serif;
--font-mono: "Cascadia Mono", "JetBrains Mono", "Consolas", ui-monospace, monospace;
--font-num:  "Segoe UI Variable Display", "Segoe UI Variable Text", sans-serif;
```

- `--font-ui`：全局默认，`body` 上声明一次。相比原栈新增 `PingFang SC`、`HarmonyOS Sans SC` 作为中文回退，覆盖华为自家系统字体命中的情况。
- `--font-mono`：**新增用途**。代码块（`.message-content pre` 之类）、模型 ID（如 `anthropic/claude-sonnet-5-5`）、Provider ID、文件路径、日志/诊断输出，统一切到等宽字体。现状这些内容都走正文字体，数字和符号对不齐。
- `--font-num`：用于强调性的大号数字或指标展示（如果后续加用量统计面板会用到），当前版本界面里没有强制要求使用，预留。

### 2.2 字号体系：建立 6 档命名令牌，禁止再出现裸的 px 字面值

现状问题：`styles.css` 里 `font-size` 直接写字面 px 值，散落在 100+ 处，产生了 8px / 9px / 10px / 11px / 12px / 13px / 14px / 15px / 16px / 17px / 18px / 24px / 25px 共 13 档毫无章法的字号，其中 **8–10px 的声明占了全部 `font-size` 规则的约 65%**，是本次重构要修复的核心问题。

新字号令牌（全部定义在 `:root`，深浅主题不覆盖字号，只覆盖颜色）：

| 令牌 | 值 | 行高 | 用途 | 对应旧值 |
|---|---|---|---|---|
| `--fs-caption` | 11px | 1.5 | 最小正文：footnote、popover 脚注、kbd、徽标文字、滑块标签 | 旧 8px / 9px |
| `--fs-label` | 12px | 1.5 | 控件标签、次要说明、小按钮文字、模型副标题 | 旧 9px / 10px |
| `--fs-body-sm` | 13px | 1.6 | 列表项、表单输入、紧凑正文（侧栏项目名、会话标题） | 旧 10px / 11px |
| `--fs-body` | 14px | 1.65 | 标准正文（消息内容、欢迎页说明、输入框文字） | 旧 12px / 13px |
| `--fs-title` | 16px | 1.3 | 卡片/面板小标题、设置弹窗导航当前项 | 旧 14px / 15px / 16px / 17px |
| `--fs-display` | clamp(26px, 2.3vw, 32px) | 1.2 | 欢迎页大标题（唯一的大字号场景） | 旧 clamp(25px,…,31px) |

**最小字号下限是 11px，全站不允许出现比这更小的 `font-size`。** 这是本次重构唯一不可妥协的硬指标——8px/9px 的内容在 100% 缩放的 1080p/1440p 屏幕上处于勉强可辨识的边界,之前测的几处（模型副标题 8px、下拉框 8px）都在反馈里被明确指出读不清。

**实现方式：** 不要求把 `font-size: 11px` 之类的值到处替换成 `var(--fs-caption)` 这种强耦合写法——用你认为维护性更好的方式落地（可以是 CSS 变量，也可以是约定好的几个工具类），但最终产出的 CSS 里，字号的离散取值必须收敛到上表 6 档以内,且不能出现小于 11px 的 `font-size`。

### 2.3 行高

现状行高从 1.1 到 1.75 不等，比较混乱。新规则：按上表每档配好的行高走，不要让字号变了但行高沿用旧值。中文为主的界面，行高宁可偏松（1.5+）不要偏紧,紧行高在中文长句下容易出现上下字行"打架"的视觉效果。

## 3. 色彩令牌：双色相 × 双明暗的完整表

### 3.1 令牌清单（两套主题结构完全一致，只有取值不同）

下表每一行是一个 CSS 变量名,右边四列是它在 4 种外观下的取值。实现方按此表直接产出 4 组 `:root` 覆盖规则（例如用 `body[data-hue="red"][data-mode="light"]` 之类的属性选择器,具体挂载方式见第 4 节)。

### 3.2 深色模式不是「反相」，是重新配色

**明确提醒实现方：不要用 `filter: invert()` 或简单的亮度反转来做深色模式。** 上表的深色列是独立配出来的,原因：

1. **背景不是纯黑**，`#13161B` / `#191314` 这种带色相倾向的深灰,比纯黑 `#000` 更不累眼,也呼应该色相的冷暖倾向（红色相的深色背景偏暖黑,蓝色相的深色背景偏冷黑)。
2. **强调色在深色下要调亮调浓**，`#C7000B` 原样放在深色背景上对比度会偏暗、不够醒目,深色版本提亮到 `#E8333D`；`#0A59F7` 深色版本提亮到 `#3D82FF`。这是因为深色背景下人眼对饱和重色的辨识度会下降,需要主动提亮而不是直接复用浅色模式的取值。
3. **文字色不是简单的黑白对调**，`--ink` 深色版本不是纯白 `#FFFFFF`,而是带一点色相倾向的米白/浅灰（`#F3E9E8` / `#E8ECF2`),纯白文字在深色大面积背景上容易产生眩光感。

### 3.3 需要重新设计的硬编码颜色（现状盘点，实现方必须逐一消化)

现有 `styles.css` 里有大量字面颜色值没有走变量，与本次重构直接冲突，必须替换为上表中的语义令牌（而不是简单保留原值然后在深色模式里打补丁）。实现方展开 `styles.css` 时会看到的典型模式包括（非完整列表，逐行过一遍文件即可发现全部）：

- 状态指示点的颜色（已连接绿、等待中琥珀黄、错误红）目前是写死的 `#6c9a76` / `#c1a16a` / `#c15c4f` 一类的值，要迁移到 `--ok` / `--warn` / `--danger`。
- 各种 `rgba(255,255,255,.XX)` 的半透明叠色（比如 `connection-card` 背景、按钮上的 `kbd` 背景)——这类写法在深色背景下会变成"浅色雾层叠在深色底上",效果和设计意图相反。这类叠色需要改成基于 `--surface` / `--surface-raised` 等不透明语义色,或者改成 `rgba(var(--ink-rgb), .XX)` 这种跟随主题反转透明度的写法（如果采用这种方式,需要额外声明 `--ink-rgb` 之类的 RGB 分量变量供 `rgba()` 拼接)。
- 滚动条颜色（`scrollbar-color: #dedcd5 transparent`）需要在深色模式下给一套更深的滚动条配色,否则深色背景上会出现刺眼的浅色滚动条。
- 焦点环颜色当前写死引用了旧的强调色 rgba 值,需要切到 `--focus-ring`。
- 输入框 placeholder 颜色、各类 `small`/`em` 弱化文字颜色,统一归到 `--ink-muted`。

**验收标准：** 重构完成后，在 `styles.css` 全文搜索 `#[0-9a-fA-F]{3,6}` 和 `rgb`/`rgba(`，命中结果应该只出现在 `:root` 的 4 组主题令牌定义块内部，正文规则里不应再有任何字面颜色值（除非是刻意不随主题变化的特例，比如 `--brand-mark`，并需要在代码注释里写明原因）。

### 3.4 SVG 图标与 PNG/静态资源

- `index.html` 内联的 `<symbol>` 图标已经都用 `fill="currentColor"` 或 `stroke="currentColor"`，天然跟随文字色走，不需要改动，保持现状写法即可（新增图标也要延续这个约定）。
- `assets/huawei.svg` 内部写死了 `fill="#FF0000"`——**这个不需要改**，因为按 3.1 节的 `--brand-mark` 规则，华为标识本来就不跟随主题切换。但要确认它在 4 套背景色下的对比度都够（尤其战狼红·浅模式下，红色标识放在偏暖白背景上，和"冷锋蓝·浅"模式下放在冷白背景上，视觉权重应该接近——如果实际看起来其中一套背景让它"糊"在一起，需要在图标外面套一个固定浅色底卡（例如白色圆底），不要改 SVG 本体颜色。

## 4. 主题的技术挂载方式（设计约束，不是实现代码）

- 用两个独立的 HTML 属性挂主题，建议 `<body data-hue="red|blue" data-mode="light|dark">`，CSS 侧用属性选择器组合出 4 套令牌覆盖（`body[data-hue="red"][data-mode="light"] { ... }` 等）。不要把色相和明暗做成 4 个互斥的主题名（如 `theme-red-light`），那样以后调一个变量要改 4 处。
- `data-mode` 支持第三个值 `auto`：此时不手动设置颜色令牌，而是写两套 `@media (prefers-color-scheme: dark)` / 不加 media query（亮色默认）的规则，让系统决定。具体是用 JS 监听 `matchMedia` 再去设实际的 `data-mode`，还是纯 CSS media query 分支，由实现方根据代码里现有的主题切换代码风格决定；两种方式选一种就好，不要混用导致状态不同步。
- 初始加载顺序要注意闪烁问题（FOUC）：主题属性应该在渲染可见内容之前就设置到 `<body>` 上，不要等 JS 异步加载完 Provider/账号数据之后才应用主题。

## 5. 用户选择的存储位置

现状代码里**没有**使用 `localStorage`/`sessionStorage`（`app.js` 全文搜索确认为空），所有持久化状态都走 `desktop/preload.cjs` 暴露的 IPC 方法，由主进程读写磁盘上的配置文件。

**结论：主题偏好（色相 + 明暗）应该走同一套 IPC 持久化路径，不要用 `localStorage`。** 理由：

1. 这是桌面应用，不是网页，`localStorage` 在 Electron 里数据存在 `Local Storage` 的 LevelDB 文件里，和这个应用现有的「配置都在 DevEco Code 管理的配置文件里」的架构不一致，会制造第二套配置存储源。
2. 现有偏好类设置（体验改进偏好、设备隐私偏好）都是通过 `privacy:get` / `privacy:set` / `privacy-device:get` / `privacy-device:set` 这类专门的 IPC 通道存取的，主题偏好应该照着这个模式新增一对通道（例如 `theme:get` / `theme:set`），而不是另起炉灐用浏览器本地存储。
3. 用户换了电脑登录同一个 DevEco 账号，或者这个应用以后要支持多工程/多窗口，`localStorage` 是跟渲染进程的"源"绑定的，容易出现"同一个应用换个入口就看不到自己设的主题"的问题；走配置文件没有这个风险。

**不要求实现方现在就去写 `desktop/main.cjs` 里的 IPC handler**——这是本文档范围之外的后端工作，这里只需要规定：渲染进程侧的主题切换逻辑要设计成"调用一个异步的 get/set 方法"的形状（哪怕先用一个内存变量占位），方便后续接上真正的 IPC，不要一上来就写成同步读写 `localStorage` 的形状，否则以后迁移要多做一次重构。

## 6. 落地顺序建议

1. 先在 `styles.css` 的 `:root` 里按第 3.1 节表格建好 4 组令牌覆盖规则 + 第 2 节的字体/字号变量，这一步不改任何业务 DOM。
2. 把现有正文规则里的硬编码颜色和裸字号 px 值，逐条替换成对令牌的引用（第 3.3 节是检查清单）。
3. 补 `--font-mono` 到代码块/模型 ID/路径类元素上（现状这些都在用正文字体）。
4. 在设置面板加两个选择器：色相（战狼红 / 冷锋蓝）+ 明暗（跟随系统 / 浅色 / 深色），接到 `data-hue` / `data-mode` 属性上。
5. 最后处理 FOUC（第 4 节）和持久化占位（第 5 节）。

每一步做完都应该能独立跑起来看效果，不需要等全部做完才能验收。
